# Инфраструктура

**Статус:** Actual
**Дата:** 2026-07-26
**Связано:** [RFC-001](RFC-001-download-confirmation-order.md), [RFC-002](RFC-002-adaptive-pacing.md), [DECISIONS.md](DECISIONS.md)

## Назначение

Описывает, из чего собран работающий сервис и как части общаются между собой:
контейнеры, границы, потоки данных, порядок запуска, поведение при отказах и
команды эксплуатации.

Архитектура **кода** (слои, порты, зависимости) — в `README.md` проекта; здесь
только то, что существует во время работы.

## Состав

Три контейнера в одной сети `docker compose`. Наружу торчит один.

```
                    ┌──────────────────────────────────────────┐
   браузер ──:80──► │ nginx 1.27-alpine                        │
                    │ единственная точка входа                 │
                    │ proxy_pass → app:8000                    │
                    └───────────────┬──────────────────────────┘
                                    │ HTTP, внутренняя сеть
                    ┌───────────────▼──────────────────────────┐
                    │ app  python:3.12-slim, uvicorn, 1 воркер │
                    │  ├─ веб-слой: страницы, /health          │      внешнее API
                    │  └─ фоновая задача обхода каталога ──────┼──────► каталога
                    └───────────────┬──────────────────────────┘   91.199.149.128:18001
                                    │ asyncpg
                    ┌───────────────▼──────────────────────────┐
                    │ db   postgres:16-alpine                  │
                    │      том pgdata                          │
                    └──────────────────────────────────────────┘
```

| Контейнер | Роль | Наружу | Состояние | Перезапуск |
|---|---|---|---|---|
| `nginx` | точка входа, реверс-прокси | `${WEB_PORT:-80}` | нет | `unless-stopped` |
| `app` | интерфейс и фоновый обход | нет | нет | `unless-stopped` |
| `db` | файлы, прогоны | нет | том `pgdata` | `unless-stopped` |

Порты `app` (8000) и `db` (5432) наружу **не публикуются** — доступны только
внутри сети compose. Единственный открытый порт хоста ведёт в nginx.

## Потоки данных

| Поток | Направление | Транспорт | Что передаётся |
|---|---|---|---|
| Просмотр страниц | браузер → nginx → app | HTTP | запросы страниц и фрагментов |
| Чтение и запись | app → db | asyncpg | файлы, счётчики цифр, состояние прогона |
| Обход каталога | app → внешнее API | HTTP | имена, ZIP-архивы, подтверждения |
| Статика | браузер → nginx → app | HTTP | CSS, JS, htmx |
| Логи | app, nginx → stdout | — | JSON-строки, забирает демон Docker |

Наружу сервис ходит ровно в одно место — API каталога. Отдаёт туда
`X-Candidate-Id` и имена файлов, полученные от него же; содержимое файлов
никуда не уходит и живёт только в `db`.

## Границы и доступы

- **Вход:** только HTTP на порт nginx. На боевом сервере ufw пропускает
  22 / 80 / 443, остальное закрыто.
- **Исход:** только к API каталога. Отдельных правил не требуется — исходящие
  разрешены.
- **Между контейнерами:** внутренняя сеть compose, имена `app` и `db` как
  DNS-имена. Пароль базы — из `.env`, наружу не публикуется.
- **SSH:** вход по ключу, парольная аутентификация и root-логин отключены
  (`deploy/provision.sh`, стадия 4).

## Состояние и данные

Состояние живёт **только** в томе `pgdata`. Контейнеры `app` и `nginx`
пересоздаются в любой момент без потерь — это и позволяет разворачивать новую
версию прямо во время многочасового обхода.

Две таблицы:

| Таблица | Что хранит | Объём на 1234 файлах |
|---|---|---|
| `files` | имя, содержимое (500 символов), счётчики цифр `d0..d9`, отметки времени | ~1.5 МБ |
| `download_runs` | статус прогона, паузы, замеры темпа | одна строка на запуск |

Диск не является узким местом: 5.8 ГБ из 25 занято, из них подавляющая часть —
образы Docker, а не данные.

## Жизненный цикл

**Порядок запуска.** `app` ждёт `db` через `condition: service_healthy` —
Postgres обязан принимать соединения раньше, чем начнутся миграции.

**Старт `app`** (`deploy/entrypoint.sh`):

1. `alembic upgrade head` — миграции применяются **до** запуска приложения.
   Окна, где новый код работает на старой схеме, не возникает.
2. `uvicorn app.main:app --workers 1 --proxy-headers`.
3. `lifespan` поднимает контейнер зависимостей и вызывает `resume_download()`:
   если в базе остался прогон в статусе `running`, обход продолжается сам.

**Один воркер uvicorn — намеренно.** Внутри процесса живёт фоновая задача
обхода. Два воркера означали бы два параллельных обхода с одного адреса, а
лимит частоты считается именно по IP: это не ускорило бы работу, а привело бы
к получасовой блокировке (см. RFC-002).

**Проверки живости:**

| Контейнер | Проверка | Интервал |
|---|---|---|
| `db` | `pg_isready` | 5 с, 10 попыток |
| `app` | `GET /health` | 30 с, 3 попытки, `start_period` 20 с |

`/health` проверяет базу настоящим запросом, а не состоянием объекта
подключения: пул отдаёт соединение и на мёртвой базе, поэтому «процесс
поднялся» — недостаточный признак готовности.

## Отказы

Формат: ситуация → что сломается → что происходит.

**`db` недоступна при старте** → миграции не применятся, `app` не поднимется →
`depends_on: service_healthy` не пустит `app` вперёд; compose будет ждать, а
`restart: unless-stopped` поднимет контейнер, когда база оживёт.

**`db` упала во время обхода** → запись файлов прервётся → сценарий пометит
прогон неуспешным, уже скачанное останется на месте; после восстановления
достаточно нажать кнопку — незавершённые файлы до-подтвердятся первым шагом.

**`app` перезапущен во время обхода** → фоновая задача умирает → прогон
остаётся `running`, `resume_download()` на старте подхватывает его и
продолжает с того же места. Проверено вживую: обход шёл 1023 → 1109 файлов
через пересоздание контейнера.

**Внешнее API недоступно** → обход не может продвинуться → клиент повторяет с
отступом 2, 4, 8… секунд, затем помечает прогон неуспешным с причиной;
интерфейс показывает её вместо молчаливого зависания.

**Внешнее API отвечает `429`/`403`** → штатная пауза, не отказ → клиент ждёт
по `Retry-After` и снижает темп (RFC-002); в интерфейсе видно причину и время
до продолжения.

**Диск заполнен логами** → контейнеры встанут → ротация настроена на уровне
демона Docker (`10m × 3` на контейнер, `deploy/provision.sh`), потолок ~90 МБ.

**Порт 80 занят на машине** → nginx не поднимется → `WEB_PORT` в `.env`
меняет внешний порт без правки compose.

**Память исчерпана** → OOM-killer → на 2 ГБ занято ~505 МБ; swap 2 ГБ настроен
в `provision.sh` как страховка на время сборки образов.

## Эксплуатация

```bash
# состояние
docker compose ps
curl -s localhost/health

# логи (JSON, одна строка на событие)
docker compose logs -f app
docker compose logs app | grep '"level": "WARNING"'

# ход обхода
docker compose exec db psql -U filestats -d filestats \
  -c "SELECT status, count(*) FROM files GROUP BY status;"

# бэкап и восстановление
docker compose exec -T db pg_dump -U filestats filestats > backup.sql
docker compose exec -T db psql -U filestats -d filestats < backup.sql

# обновление версии без простоя данных
docker compose up -d --build       # пересоздаётся только app, том остаётся
```

Данные восстановимы и без бэкапа: каталог отдаёт содержимое заново любому
новому `CATALOG_API__CANDIDATE_ID`, полный обход занимает ~11 минут.

## Первичная настройка сервера

`deploy/provision.sh`, четыре идемпотентные стадии:

| Стадия | Что делает |
|---|---|
| 1 | обновление системы, swap 2 ГБ, пользователь `app` с ключом |
| 2 | Docker CE + compose, uv, ограничение логов |
| 3 | ufw (22/80/443), fail2ban, автообновления безопасности |
| 4 | отключение парольного входа и root-логина |

Стадия 4 отказывается выполняться, если `authorized_keys` пуст хотя бы у
одного из пользователей: закрыть парольный вход, не убедившись в работающем
ключе, — верный способ потерять доступ к серверу.

## Верификация

```bash
docker compose ps
# app, db — Up (healthy); nginx — Up

curl -s localhost/health
# {"status":"ok","database":"ok","download":"completed","worker_running":false}

curl -s -o /dev/null -w "%{http_code}\n" localhost/
# 200

docker compose logs app | grep -c "Running upgrade"
# ≥1 — миграции применились при старте

docker compose exec -T db psql -U filestats -d filestats -t \
  -c "SELECT count(*), min(length(content)), max(length(content)) FROM files;"
# 1234 | 500 | 500
```
