# RFC-003: Перенос замеров темпа в схему хранения

**Статус:** Implemented
**Дата:** 2026-07-26
**Связано:** `docs/RFC-002-adaptive-pacing.md`, `migrations/versions/56e39606f853_run_pacing_measurements.py`

## Motivation

Каталог не публикует свой лимит частоты (см. RFC-002), поэтому единственный
способ о нём судить — измерять собственный трафик. Первая реализация считала
показатели в памяти процесса (`DownloadMetrics`) и выводила их одной строкой в
лог по завершении обхода.

Это дало ложные данные при первой же проверке. Итоговая запись боевого прогона:

```json
{"event": "run.completed", "run_id": 1, "files_saved": 155, ...}
```

при фактических **1234** скачанных файлах. Причина: контейнер пересоздавался в
середине обхода, прогон корректно продолжился с того же места (RFC-001), а
счётчики в памяти начались заново и описали только последний запуск процесса.

Строка «прогон завершён, сохранено 155 файлов» при 1234 файлах — не неточность,
а неверное утверждение в логе, на которое кто-то может опереться.

Второй мотив: показатели темпа нужны в интерфейсе. Оценка границы лимита — то,
ради чего они собираются, — не должна требовать чтения логов через SSH.

## Problem

Как считать показатели обхода так, чтобы они описывали весь прогон целиком, а
не отрезок между двумя перезапусками процесса, и были доступны интерфейсу.

## Goals

- Показатели переживают перезапуск процесса — измеряется
  `tests/unit/test_download_service.py::test_pacing_accumulates_across_a_restart`.
- Наблюдавшийся темп доступен в интерфейсе без чтения логов — измеряется
  наличием блока на главной странице и
  `tests/unit/test_run_pacing.py::test_view_formats_measured_numbers`.
- Отсутствие данных отображается как отсутствие, а не как нули — измеряется
  `test_fresh_run_has_no_pacing_data`.
- Показанное число не выдаётся за опубликованный лимит — обеспечивается
  формулировкой в интерфейсе и проверяется
  `test_verdict_reflects_whether_the_boundary_was_touched`.

## Non-Goals

- **Хранение истории замеров по шагам (временной ряд)** — вне объёма. Для
  оценки границы достаточно агрегата за прогон; временной ряд потребовал бы
  отдельной таблицы и политики хранения ради задачи, которой нет.
- **Экспорт метрик в Prometheus/OpenTelemetry** — вне объёма. Один сервис на
  одном хосте; см. решение по стеку сбора логов в разделе Alternatives.
- **Сохранение прикладных счётчиков (`files_saved`, `files_confirmed`) в базу**
  — вне объёма. Достоверный итог по файлам уже есть в таблице `files` и
  показывается в интерфейсе; дублировать его в прогоне значило бы завести два
  источника правды. В логе они остались с префиксом `cycle_`, честно
  обозначающим область — текущий запуск процесса.

## Solution

**Слой domain** (`app/domain/run.py`) — агрегат `DownloadRun` получает четыре
поля и метод их приёма:

```python
requests_made: int = 0
throttle_events: int = 0
seconds_paused: float = 0.0
interval_seconds: float | None = None

def record_pacing(self, *, requests, throttles, paused, interval) -> None
```

Там же — производные величины: `elapsed_seconds` (от старта до завершения или
последней активности) и `requests_per_minute`. Расчёт живёт в домене, потому
что это правило предметной области, а не форматирование.

**Слой application** (`app/application/ports.py`) — порт `CatalogClient`
дополнен методом `pacing() -> PacingSnapshot`. Прикладной слой вправе знать,
каким темпом идёт обращение к каталогу: это часть контракта, а не деталь
реализации HTTP.

**Ключевое решение — базовая точка.** Клиент считает запросы от собственного
старта, а прогон переживает рестарт. Сценарий запоминает то, что прогон
накопил до текущего запуска, и прибавляет к нему показания клиента:

```python
self._baseline = PacingSnapshot(
    requests_made=run.requests_made, ...   # снимается один раз в execute()
)
...
run.record_pacing(requests=self._baseline.requests_made + snapshot.requests_made, ...)
```

Без базовой точки перенос в базу воспроизвёл бы ровно ту же ошибку, от которой
затевался.

**Слой infrastructure** — `HttpCatalogClient` ведёт три счётчика; запись в
прогон происходит там же, где сценарий и так сохраняет прогресс
(`_save_with_pacing`), то есть без дополнительных обращений к базе.

**Слой presentation** — `PacingViewModel` форматирует числа и формирует
словесный вывод. Формулировка подчёркивает природу данных: показано
**наблюдавшееся**, а не заявленное.

**Поток данных:**

```
HttpCatalogClient (счётчики) -> PacingSnapshot -> DownloadRun -> download_runs -> PacingViewModel
```

**Схема хранения** — миграция `56e39606f853`, четыре колонки в
`download_runs`, все с `server_default`, чтобы существующие строки остались
валидными.

## Alternatives

**Вариант B — оставить счётчики в памяти, а в итоговую строку добавить
достоверные числа из таблицы `files`.** Лучше тем, что не требует миграции
вовсе. Отвергнут частично — именно так и поступили с прикладными счётчиками
(см. Non-Goals). Но для показателей темпа он не работает: число запросов и
отказов нигде, кроме клиента, не known, из таблицы файлов его не восстановить.

**Вариант C — отдельная таблица `run_pacing_samples` с записью на каждый
запрос.** Лучше детальностью: видно, как менялся интервал по ходу обхода,
можно построить график. Отвергнут по стоимости: +630 вставок на обход ради
данных, которые нужны в агрегированном виде, плюс политика удаления старых
строк. Для оценки границы достаточно четырёх чисел.

**Вариант D — развернуть Prometheus и экспортировать метрики.** Лучше тем, что
даёт стандартный инструментарий, историю и алерты. Отвергнут по соразмерности:
на 2 ГБ памяти стек наблюдения стал бы самым прожорливым компонентом системы —
больше, чем сам сервис. Задачу агрегации по многим хостам, ради которой он
существует, здесь решать не для чего: хост один. То же соображение ранее
отвергло связку Loki + Promtail + Grafana; JSON-логи оставляют эту дорогу
открытой, если сервисов станет больше.

**Ничего не делать.** Статус-кво — итоговая строка лога, которая после любого
перезапуска сообщает неверные числа, не помечая их как частичные. Это хуже
отсутствия метрик: отсутствующим данным не доверяют, а неверным — доверяют.

## Risks

**Строка лога уже была опубликована с неверными числами** -> кто-то мог на неё
опереться -> поля прикладных счётчиков переименованы в `cycle_*`, что делает
их область явной прямо в имени; покрыто
`test_metrics.py::test_log_fields_are_scoped_to_the_process_cycle`.

**Показатель принимают за опубликованный лимит сервиса** -> ложные выводы о
работе стороннего API -> формулировка в интерфейсе прямо говорит, что это
измерения собственного трафика, а не заявленное значение; в
`PacingViewModel` это зафиксировано докстрокой и текстом вывода.

**Прогон прерван, `elapsed_seconds` не определён** -> деление на ноль ->
`requests_per_minute` возвращает `None`, интерфейс показывает прочерк;
покрыто `test_rate_is_unknown_without_elapsed_time`.

**Замеры отсутствуют (старый прогон до миграции)** -> блок с нулями вводит в
заблуждение -> `has_pacing_data` возвращает `False`, `PacingViewModel.build()`
отдаёт `None`, блок не отрисовывается вовсе.

**Параллельный запуск** -> два клиента пишут в один прогон -> невозможен по
построению (RFC-001).

**Деньги** — API бесплатный.

**Приватность** — в базу пишутся только счётчики и длительности, никаких
внешних данных.

**Судьба накопленных данных** — миграция только добавляет колонки со
значениями по умолчанию. Существующие 1234 файла и запись прогона `#1`
остались нетронутыми; у прогона `#1` показатели равны нулю, и интерфейс
корректно показывает отсутствие данных вместо нулей.

## Migration

Миграция `56e39606f853` (`8201cd8ca817 -> 56e39606f853`), четыре
`ADD COLUMN` с `server_default`.

**Пере-сборка данных не требуется** — миграция аддитивна, содержимое файлов не
затрагивается. Занимает доли секунды: `ALTER TABLE ... ADD COLUMN` с
константным умолчанием в PostgreSQL 11+ не переписывает таблицу.

**Совместимость старых записей** — полная. Строка прогона `#1`, созданная до
миграции, читается новым кодом: колонки заполнены нулями, `has_pacing_data`
возвращает `False`, блок показателей не рисуется. Конвертер не нужен.

**Промежуточное состояние** — есть и безопасно: новая схема с колонками
работает со старым кодом (он их просто не читает), а новый код со старой схемой
не поднимется, поэтому порядок шагов однозначен.

**Порядок развёртывания:**

1. `alembic upgrade head` — выполняется в `deploy/entrypoint.sh` **до** старта
   приложения. Окна, где новый код видит старую схему, не возникает.
2. `docker compose up -d --build` — приложение стартует уже на новой схеме.
3. Незавершённый прогон, если он был, подхватывается с базовой точкой
   `requests_made = 0` — это корректно: замеров до миграции не существовало.

**Заполнение данными.** Показатели появляются только у прогонов, отработавших
после миграции. Для получения реальных измерений выполнен повторный обход под
новым `CATALOG_API__CANDIDATE_ID` (API поддерживает это штатно, выдавая полный
каталог новому идентификатору). Таблицы при этом очищаются, данные
восстанавливаются тем же обходом за ~11 минут.

## Rollback

**Откат кода:** вернуть предыдущий образ и выполнить
`alembic downgrade 8201cd8ca817`. `downgrade()` в миграции реализован и
проверен — прогонялся цикл `upgrade -> downgrade -> upgrade` на чистой базе.
Четыре `DROP COLUMN` теряют только замеры; файлы, прогоны и их статусы
сохраняются.

**Быстрое отключение без отката схемы:** колонки можно оставить, а блок в
интерфейсе исчезнет сам, если показатели нулевые. Отдельный флаг не заводился —
он дублировал бы `has_pacing_data`, который уже отвечает на тот же вопрос по
данным, а не по конфигурации.

**Бэкап до миграции:**

```bash
docker compose exec -T db pg_dump -U filestats filestats > backup-pre-56e39606f853.sql
```

Данные восстановимы и без него: каталог отдаёт содержимое заново любому новому
`CATALOG_API__CANDIDATE_ID`, полный обход занимает ~11 минут.

**Данные, накопленные новой схемой** — четыре числа на прогон. Ценности вне
контекста этого RFC не представляют, при откате удаляются без последствий.

## Ревью

Codex недоступен, проведено само-ревью. Зафиксированные развилки:

1. **Где хранить замеры** — решение: в записи прогона. Отвергнуто: в памяти
   процесса — именно это дало неверную строку лога, с которой начался RFC.
2. **Как складывать показания клиента с накопленным** — решение: базовая точка,
   снимаемая один раз при старте сценария, плюс абсолютная запись в агрегат.
   Отвергнуто: инкрементальные прибавки на каждом сохранении — они дают
   двойной учёт при любом повторе, а повторы здесь штатны.
3. **Дублировать ли в прогон прикладные счётчики файлов** — решение: нет,
   достоверный итог в таблице `files`. Отвергнуто: сохранять и их — два
   источника правды об одном и том же.
4. **Как назвать поля лога, оставшиеся в памяти** — решение: префикс `cycle_`.
   Отвергнуто: оставить прежние имена и объяснить область в документации —
   читатель лога документацию не открывает.
5. **Разворачивать ли полноценный сбор метрик** — решение: нет, четыре числа в
   прогоне. Отвергнуто: Prometheus и Loki-стек — на 2 ГБ они стали бы крупнее
   наблюдаемого сервиса.
