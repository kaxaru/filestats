# RFC-001: Порядок подтверждения скачивания

**Статус:** Implemented
**Дата:** 2026-07-26
**Связано:** `docs/RFC-002-adaptive-pacing.md`, `app/application/download_service.py`, `app/domain/file.py`

## Motivation

Каталог отдаёт имена файлов порциями и требует отдельно подтверждать факт
скачивания через `POST /api/files/downloaded`. Подтверждение **необратимо**:
после него имя больше никогда не попадёт в выдачу `GET /api/files/names`, а
служебная ручка сброса прогресса закрыта админским токеном, которого у нас нет.

Цена ошибки прямая и невосполнимая: подтвердили имя, содержимое которого не
сохранили, — файл потерян навсегда, и восстановить его нечем. При каталоге в
1234 файла и обходе длиной 11 минут окно для такой ошибки открыто всё время
работы.

Наивная реализация («скачал — отметил — сохранил») выглядит естественно и
ломается на первом же падении процесса между вторым и третьим шагом.

## Problem

Как гарантировать, что необратимое подтверждение на стороне каталога никогда
не опередит сохранение содержимого в нашем хранилище — включая падение
процесса, перезапуск контейнера и сетевой сбой в любой точке обхода.

## Goals

- Ни один файл не подтверждается без сохранённого содержимого — измеряется
  тестом `tests/unit/test_download_service.py::test_confirmation_never_precedes_saving`,
  который проверяет состояние хранилища в момент каждого вызова подтверждения.
- Прерывание процесса в любой точке не приводит к потере данных — измеряется
  `tests/e2e/test_full_flow.py::test_interrupted_run_is_resumed_on_startup`.
- Повторная выдача уже скачанных имён не вызывает повторного скачивания —
  измеряется `test_already_saved_names_are_not_downloaded_again`.
- Обход завершается за конечное время при любом поведении каталога —
  измеряется `test_stalled_traversal_stops_instead_of_looping_forever`.

## Non-Goals

- **Транзакционность между нашей базой и внешним API** — вне объёма.
  Распределённой транзакции здесь быть не может: каталог не умеет ни двухфазный
  коммит, ни отмену подтверждения. Решение строится на том, что одно из
  состояний (сохранено, но не подтверждено) безопасно, и обход к нему сводится.
- **Возобновление конкретного HTTP-запроса после падения** — вне объёма.
  Единица восстановления — файл, а не запрос: недокачанная тройка просто
  запрашивается заново, это дешевле любой машинерии докачки.
- **Параллельное скачивание в несколько потоков** — вынесено в RFC-002,
  где показано, что оно не ускоряет обход, а приближает бан.

## Solution

Порядок шагов зафиксирован структурно, а не соглашением:

```
GET /names -> POST /download -> сохранение в БД (commit) -> POST /downloaded
```

**Слой domain** (`app/domain/file.py`) — агрегат `CatalogFile` с односторонним
жизненным циклом:

| Статус | Что означает |
|---|---|
| `discovered` | имя получено, содержимого нет |
| `downloaded` | содержимое у нас, каталогу не сообщали |
| `marked` | каталог подтвердил, имя больше не выдаст |

Переходы разрешены только вперёд, а `confirm_marked()` возбуждает
`ContentRequired`, если содержимого нет. Это не проверка «на всякий случай»:
она делает недопустимое состояние невыразимым в коде.

**Слой application** (`app/application/download_service.py`) — сценарий
`CatalogDownloadService`. Ключевое решение: метод `_confirm_saved()` берёт
имена для подтверждения **из хранилища**, а не из переменной в памяти:

```python
batch = await self._files.awaiting_confirmation(self._confirm_batch_size)
outcome = await self._client.confirm_downloaded([file.name for file in batch])
```

Запрос `awaiting_confirmation` возвращает только записи со статусом
`downloaded`, то есть уже закоммиченные вместе с содержимым. Подтвердить
несохранённое физически неоткуда взять.

**Поток данных:**

```
CatalogClient -> CatalogDownloadService -> FileRepository (commit) -> CatalogClient.confirm
```

**Асимметрия состояний.** Из двух возможных рассогласований опасно только
одно, и порядок выбран так, чтобы система всегда оказывалась в безопасном:

| Состояние | Последствие |
|---|---|
| Подтверждено, но не сохранено | **Потеря файла навсегда** |
| Сохранено, но не подтверждено | Каталог предложит имя снова, мы его узнаем и до-подтвердим |

Второе состояние обрабатывается явно: если все предложенные имена уже есть в
базе, сценарий не считает это тупиком, а сбрасывает накопленные подтверждения
и продолжает. Без этой ветки цикл не завершился бы никогда.

**Пачки подтверждений.** У `POST /downloaded` нет ограничения на количество
имён — в отличие от `POST /download` с жёстким пределом в 3 файла. Это
позволяет закрывать несколько троек одним запросом (по умолчанию 30) и
сокращает общее число обращений примерно на треть. Безопасность не страдает:
неподтверждённые файлы уже сохранены.

## Alternatives

**Вариант B — подтверждать сразу после получения ZIP, до записи в базу.**
Лучше тем, что имя быстрее уходит из выдачи и следующая порция не содержит
повторов, то есть меньше «холостых» запросов имён. Отвергнут: любое падение
между ответом каталога и коммитом в базу теряет до трёх файлов безвозвратно.
Выигрыш в единицах запросов не стоит невосполнимых данных.

**Вариант C — хранить «журнал намерений»: сначала писать в отдельную таблицу
«собираюсь подтвердить», затем подтверждать, затем помечать.** Лучше тем, что
даёт явный аудит попыток и позволяет разобрать частичные сбои. Отвергнут как
переусложнение: журнал решает ту же задачу, что и статус `downloaded` в самой
записи файла, но ценой второй таблицы, второго набора инвариантов и
рассинхронизации между ними. Статус в агрегате — тот же журнал, только без
дубликата состояния.

**Вариант D — подтверждать по одному файлу сразу после его сохранения.**
Лучше предсказуемостью: окно между сохранением и подтверждением минимально.
Отвергнут по стоимости: это +1 запрос на каждый файл, то есть примерно
1234 дополнительных обращения на полный обход при жёстком лимите частоты —
обход удлинился бы вдвое ради устранения окна, которое и так безопасно.

**Ничего не делать (наивный порядок).** Статус-кво без этого решения — код,
который работает на счастливом пути и молча теряет файлы при первом сбое.
Обнаруживается это не сразу: каталог перестаёт предлагать имя, у нас его нет,
и никакой ошибки при этом не возникает. Тихая потеря данных хуже громкого
падения.

## Risks

**Каталог недоступен в момент подтверждения** -> файлы остаются в статусе
`downloaded`, обход прерывается -> при следующем запуске `_confirm_saved()`
вызывается первым шагом и закрывает хвост; операция идемпотентна, повтор
безопасен (ответ содержит `already_marked`).

**Процесс убит между сохранением и подтверждением** -> то же безопасное
состояние -> `resume_download()` на старте приложения подхватывает
незавершённый прогон, первым делом до-подтверждает накопленное.

**Пустой ответ ручки имён на старте** -> обход завершается немедленно со
статусом `completed` -> это корректное поведение: пустой список и есть
единственный признак полноты каталога, отдельной проверки не требуется.

**Параллельный запуск двух обходов** -> оба конкурируют за одни и те же имена,
удваивают запросы и приближают бан -> `DownloadLauncher.begin()` возвращает уже
идущий прогон вместо создания нового, `BackgroundWorker.spawn()` не плодит
задачу, если предыдущая жива. Покрыто
`test_second_launch_returns_the_same_run`.

**Файл числится в выдаче, но отсутствует в каталоге (404)** -> его нельзя ни
скачать, ни подтвердить, и каталог предлагает его снова и снова -> обнаружение
затыка: три круга подряд без единого сохранённого или подтверждённого файла
останавливают прогон с `DownloadStalled` и перечислением застрявших имён.
Без этой защиты был бы бесконечный цикл.

**Деньги** — внешний API бесплатный, риск неприменим.

**Приватность** — наружу уходят только имена файлов, полученные от самого же
каталога. Содержимое (строки цифр) никуда не передаётся, живёт в Postgres на
том же сервере.

**Судьба накопленных данных** — таблица `files` переживает перезапуск и
пересборку контейнера (том `pgdata`). Повторный запуск обхода не стирает
скачанное: `register_discovered` использует `ON CONFLICT DO NOTHING`, что
проверено `test_repeated_registration_does_not_wipe_content`.

## Migration

Решение внедрено с первой версии сервиса, миграции с предыдущей схемы не
требовалось. Порядок развёртывания для чистой установки:

1. `alembic upgrade head` — создаёт `files` со статусами и `download_runs`.
   Выполняется автоматически в `deploy/entrypoint.sh` до старта приложения.
2. Приложение поднимается, `resume_download()` не находит активных прогонов.
3. Обход запускается кнопкой.

Пере-сборка данных не нужна: каталог отдаёт содержимое заново любому новому
`CATALOG_API__CANDIDATE_ID`. Полный обход занял 11 мин 07 с на 1234 файлах.

Промежуточное состояние, где работали бы обе схемы, отсутствует — статусы
введены сразу, старого формата не существует.

## Rollback

Откат этого решения означал бы возврат к порядку с риском потери данных и
поэтому не предусмотрен как штатная операция. Что действительно отменяемо:

- **Размер пачки подтверждений** — переменная `DOWNLOAD__CONFIRM_BATCH_SIZE`
  в `.env`. Значение `1` возвращает поведение «подтверждать сразу после каждой
  сохранённой тройки», без изменения кода и без потери безопасности.
- **Остановка обхода** — `docker compose stop app`. Прогон остаётся в статусе
  `running`, данные сохранены, при следующем старте работа продолжится.
- **Возврат к предыдущему образу** — `docker compose up -d --build` с
  предыдущим тегом. Схема данных совместима: статусы не менялись между
  версиями.
- **Бэкап перед миграциями** — `docker compose exec db pg_dump -U filestats
  filestats > backup.sql`. Данные восстановимы и без бэкапа: достаточно
  очистить таблицы и запустить обход с новым идентификатором кандидата.

Флага мгновенного отключения фичи нет и не требуется: порядок подтверждения —
не фича, а свойство корректности, отключать его нечем и незачем.

## Ревью

Codex недоступен, проведено само-ревью. Зафиксированные развилки:

1. **Откуда брать имена для подтверждения** — решение: из хранилища
   (`awaiting_confirmation`). Отвергнуто: из списка в памяти сценария, который
   пришлось бы синхронизировать с базой вручную и который не переживает
   рестарт.
2. **Где живёт запрет на подтверждение без содержимого** — решение: в агрегате
   `CatalogFile`. Отвергнуто: проверка в сценарии — она защищала бы только тот
   путь, где её не забыли написать.
3. **Что делать с файлом, которого нет в каталоге** — решение: пропустить и
   отследить общий затык. Отвергнуто: уронить весь обход (теряется прогресс по
   исправным файлам) и «пропустить молча» (бесконечный цикл).
