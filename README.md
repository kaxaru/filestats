# Сервис скачивания и анализа файлов

Скачивает каталог текстовых файлов через ограниченное по частоте API и считает
статистику по цифрам в их содержимом.

## Быстрый старт

```bash
cp .env.example .env
# в .env обязательно поменяйте CATALOG_API__CANDIDATE_ID — см. ниже
docker compose up -d --build
```

Интерфейс — на `http://localhost/`. Миграции применяются автоматически при
старте контейнера. Ничего, кроме Docker, не нужно: ни Python, ни Postgres на
машине.

### Обязательно: свой идентификатор кандидата

Каталог отдаёт каждый файл **ровно один раз на `CATALOG_API__CANDIDATE_ID`**.
С уже использованным значением ручка имён сразу вернёт пустой список: обход
завершится за секунду с нулём файлов и статусом «каталог скачан полностью».
Формально это правильный ответ, но выглядит как поломка.

Поэтому в `.env` подставьте любую свою уникальную строку. Если всё же
запустите с чужим идентификатором, сервис скажет об этом прямо на странице
скачивания и в логе — искать причину не придётся.

### Если порт 80 занят

```bash
echo "WEB_PORT=8080" >> .env
docker compose up -d
```

### Тесты

Нужен Postgres. Поднимается одной командой, на порту 5433, чтобы не спорить с
уже установленным на машине:

```bash
docker run -d --rm --name filestats-test-db \
  -e POSTGRES_USER=filestats -e POSTGRES_PASSWORD=filestats \
  -e POSTGRES_DB=filestats_test -p 5433:5432 postgres:16-alpine

uv sync
uv run pytest          # 5433 — значение по умолчанию, переменные не нужны
uv run ruff check .
```

Адрес базы переопределяется через `TEST_DATABASE_URL`. Убрать за собой:
`docker rm -f filestats-test-db`.

### Секреты

В репозитории нет ни одного рабочего значения: `.env` игнорируется, а
`.env.example` содержит только плейсхолдеры. Пароль базы и идентификатор
кандидата живут в `.env` на машине, где сервис запущен.

`.gitignore` покрывает `.env`, приватные ключи, сертификаты и дампы базы —
последнее не формальность: README предлагает делать `pg_dump` прямо в каталоге
проекта. Правила и команда самопроверки перед первым коммитом — в комментариях
`.gitignore`.

## Что внутри

Две страницы:

1. **Скачивание** — кнопка «Скачать данные», время старта по Новосибирску,
   счётчики «получено N названий / скачано M из N», состояние процесса и
   причина паузы, если сервис упёрся в лимит.
2. **Файлы и расчёты** — список скачанных файлов с временем скачивания,
   сортировкой и пагинацией, выбор файлов (точечно, вся страница, весь
   каталог) и кнопка «Произвести расчёты»: общая статистика по цифрам и
   разбивка по каждому файлу.

## Инфраструктура

Три контейнера в одной сети `docker compose`; наружу торчит только nginx.

```
браузер ──:80──► nginx ──► app (uvicorn, 1 воркер) ──► db (postgres, том pgdata)
                            └──► внешнее API каталога
```

| Контейнер | Роль | Наружу | Состояние |
|---|---|---|---|
| `nginx` | точка входа, реверс-прокси на `app:8000` | `${WEB_PORT:-80}` | нет |
| `app` | интерфейс и фоновый обход каталога | нет | нет |
| `db` | файлы и прогоны | нет | том `pgdata` |

Состояние живёт только в `db`, поэтому `app` и `nginx` пересоздаются в любой
момент — прерванный обход подхватывается из базы и продолжается с того же
места. Именно это позволяет разворачивать новую версию прямо во время
многочасового скачивания.

Подробно — порядок запуска, проверки живости, поведение при отказах, команды
эксплуатации: **[docs/infrastructure.md](docs/infrastructure.md)**.

## Архитектура

```
app/
  domain/           агрегаты, объекты-значения, инварианты — без БД и HTTP
  application/      порты (протоколы) и сценарии
  infrastructure/   реализации портов: HTTP-клиент каталога, хранилище
  presentation/     тонкие контроллеры, ViewModel'и, шаблоны, статика
  container.py      композиционный корень: единственное место сборки
```

Зависимости направлены внутрь: `presentation → application → domain`,
`infrastructure → application`. Домен не импортирует ничего из проекта, кроме
себя самого.

Что это даёт на практике:

- сценарий обхода каталога проверяется целиком на подставных портах — без базы,
  без сети и без ожиданий в реальном времени;
- e2e-тесты поднимают тот же самый стек, подменив только клиент каталога;
- ошибки, пересекающие границу порта, объявлены в `application/errors.py`,
  поэтому сценарии ловят их, не зная про `httpx`.

Маппинг на таблицы **императивный** (`infrastructure/persistence/orm.py`):
доменные классы не наследуют базу SQLAlchemy и не знают о существовании ORM.

## Инварианты

Ради них домен и выделен в отдельный слой.

**1. Файл нельзя подтвердить на сервере, пока его содержимое не сохранено.**

Отметка через `POST /api/files/downloaded` необратима: отмеченное имя больше
никогда не попадёт в выдачу. Отметить файл, содержимого которого у нас нет, —
значит потерять его навсегда. Поэтому порядок строгий:

```
получили имена → скачали → сохранили в БД → и только теперь подтвердили
```

Инвариант защищён не комментарием «не забыть про порядок», а устройством кода:
`_confirm_saved()` берёт имена для подтверждения из самого хранилища, а
`CatalogFile.confirm_marked()` отказывается работать без содержимого.

**2. Статус файла движется только вперёд:** `discovered → downloaded → marked`.

**3. Счётчики цифр не расходятся с содержимым** — они вычисляются ровно в той
точке, где содержимое присваивается агрегату, и больше нигде.

**4. Активный прогон ровно один**, терминальный статус окончателен.

## Ключевые решения

### Частота запросов

API не публикует свои лимиты: на успешных ответах нет ни одного заголовка вида
`X-RateLimit-*`. Единственный источник сведений — отказы. Поэтому темп
подбирается на ходу и **асимметрично**: ускоряемся медленно (после серии
успешных запросов, с коэффициентом), тормозим резко (кратно, при первом же
отказе). Цена лишнего запроса — получасовой бан, цена лишней паузы — доли
секунды, и подстройка это учитывает.

`Retry-After` поддерживается в обоих форматах спецификации — и число секунд, и
HTTP-дата, потому что сервер про свой выбор не сообщает.

Ждать бесконечно нельзя: после `max_consecutive_throttles` подряд идущих
отказов прогон останавливается с внятной причиной, а не висит сутками молча.

**Где проходит граница.** Каталог её не публикует, поэтому она выведена из
собственного трафика полного обхода: 1234 файла, 763 запроса за 10 мин 49 с,
средний темп 70.5 запросов в минуту, двенадцать `429` и **ни одной**
блокировки. После каждого отступа к интервалу 1.00 с (60 запросов в минуту)
отказы прекращались, а разгон ниже ~0.55 с (более 109 в минуту) вызывал их
стабильно. Это оценка по наблюдениям, а не заявленное значение — в интерфейсе
она подписана именно так.

### Один процесс, без параллелизма

Троттлинг считается по IP-адресу, а прогресс — по `X-Candidate-Id` (это видно
по служебным ручкам: `/api/admin/candidates/{id}/progress` против
`/api/admin/clients/{ip}/throttling`). Сменой идентификатора лимит не обойти,
поэтому распараллеливание не ускорило бы работу, а лишь приблизило бы бан.
Клиент однопоточный by design.

### Пачки отметок

У `POST /api/files/downloaded` нет ограничения на количество имён — в отличие
от скачивания, где жёсткий предел в 3 файла. Это позволяет закрывать несколько
троек одним запросом и заметно сокращает общее время обхода. Слишком большая
пачка невыгодна: неподтверждённые имена продолжают возвращаться в выдаче и
тратят запросы впустую.

### Неполные пачки

`POST /api/files/download` отвечает `404`, если хотя бы одного имени из тройки
нет в каталоге — падает вся тройка. Клиент в этом случае пересобирает запрос
поштучно, чтобы два исправных файла не пропали из-за одного битого.

### Завершение

Общее количество файлов сервис не сообщает, поэтому единственный признак
полноты — пустой ответ ручки имён. Знаменатель прогресса в интерфейсе — не
размер каталога, а число уже увиденных имён; это честно отражено в подписи.

Отдельный случай: каталог может вернуть имена, которые у нас уже есть, но ещё
не подтверждены. Без обработки этого случая цикл никогда бы не завершился —
сервис до-подтверждает накопленное и продолжает.

### Восстановление после рестарта

Полный обход идёт часами. Состояние прогона живёт в БД, а не в памяти процесса:
при старте приложения незавершённый прогон подхватывается автоматически, а
файлы, сохранённые но не подтверждённые, до-подтверждаются первым же шагом.

### Расчёты

Счётчики цифр считаются один раз, при сохранении файла, и лежат в колонках
`d0..d9`. «Произвести расчёты» превращается в один `SUM` на стороне БД вместо
повторного разбора пятисотсимвольных строк на каждый клик.

Выбор «вообще все» передаётся признаком области, а не списком имён:
перечислять тысячи значений в теле запроса незачем, когда на стороне хранилища
это просто отсутствие условия.

Разбивка по файлам листается постранично — так же, как список файлов, и по тем
же причинам: тысячи строк не нужны ни экрану, ни ответу, но и прятать их за
«показаны первые N» незачем, доступ должен быть ко всем. Нумерация строк
сквозная. Общий итог при этом всегда считается по всей выборке, а не по
видимой странице: это один агрегат на стороне базы, его стоимость от числа
выбранных файлов не зависит.

Страницы разбивки перезапрашиваются вместе с формой выбора (`hx-include`),
иначе переход на вторую страницу терял бы отмеченные файлы.

## Наблюдаемость

Логи — JSON, одна строка на событие (`LOGGING__FORMAT=text` для локальной
разработки). Формат сам по себе бесполезен без связности, поэтому есть
ASGI-middleware: он присваивает запросу идентификатор, кладёт его в
`contextvar` и через фильтр логирования проставляет во **все** записи внутри
этого запроса, включая сообщения из глубины сценариев.

```json
{"ts":"...","level":"INFO","logger":"app.access","message":"GET /files -> 200",
 "event":"http.request","method":"GET","path":"/files","status":200,
 "duration_ms":28.7,"request_id":"trace-me-123"}
```

Идентификатор подхватывается из входящего заголовка `X-Request-ID`, если его
проставил прокси, и возвращается в ответе — по нему пользователь может назвать
конкретный запрос, а мы найдём его в логах. Проверки живости и статика в
access-лог не пишутся: раз в полминуты плюс запрос на каждый переход — это шум,
который прячет полезное.

По завершении обхода пишется итоговая строка: сколько раз упёрлись в лимит,
сколько минут простояли в паузах, сколько файлов прошло через процесс. После
долгой работы важно не «готово», а чем именно это далось — иначе подбирать
темп не на чем.

Эти поля названы `cycle_*` намеренно. Прогон переживает рестарт контейнера, а
счётчики живут в памяти и после возобновления начинаются заново — то есть
описывают работу текущего процесса, а не весь прогон. Достоверный итог по
каталогу лежит в таблице файлов и показывается в интерфейсе; путать одно с
другим не следует, поэтому имена полей об этом прямо говорят.

`GET /health` проверяет базу настоящим запросом, а не состоянием объекта
подключения: пул отдаёт соединение и на мёртвой базе. Этот же эндпоинт
использует healthcheck в compose.

Отдельный стек сбора логов (Loki, Promtail, Grafana) сознательно не
разворачивался: на 2 GB он стал бы самым прожорливым компонентом системы,
а задачу агрегации по многим хостам, ради которой он существует, здесь решать
не для чего — сервис один. Ротация логов Docker настроена в `provision.sh`
(`10m × 3`). JSON-формат оставляет эту дорогу открытой, если сервисов станет
больше.

## Тесты

```bash
uv run pytest
```

| Уровень | Что проверяет |
|---|---|
| `tests/unit` | Инварианты домена, счётчики, подбор темпа, разбор `Retry-After`, клиент каталога на замоканном HTTP, сценарий обхода целиком на подставных портах |
| `tests/integration` | Репозитории и запросы чтения против настоящего Postgres |
| `tests/e2e` | Полный стек: приложение, база, маршруты, шаблоны — против заглушки каталога |

Заглушка в e2e стоит не ради скорости: боевой каталог отдаёт каждый файл ровно
один раз, и прогонять по нему тесты значило бы безвозвратно расходовать данные
задания.

Паузы в тестах не выдерживаются — `asyncio.sleep` подменяется, а запрошенные
длительности записываются и проверяются. Проверяется логика ожидания, а не
терпение.

Адрес тестовой базы задаётся переменной `TEST_DATABASE_URL`.

## Настройки

Сгруппированы по назначению в `app/config.py`: `catalog_api`, `pacing`,
`download`, `web`. Переопределяются через `.env` с разделителем `__`,
например `PACING__INITIAL_INTERVAL_SECONDS=2`.

Ограничения, которые диктует внешнее API (не более трёх файлов за запрос,
получасовой бан, длина содержимого), в настройки не вынесены: крутить их
бессмысленно, сервер всё равно ответит отказом. Они живут в
`app/domain/values.py` как именованные константы.

## Развёртывание

`deploy/provision.sh` — первичная настройка сервера, разбитая на стадии:
система и swap, Docker и uv, firewall и fail2ban, отключение парольного входа.
Скрипт идемпотентен, а стадия хардening отказывается выполняться, если не
убедится, что вход по ключу возможен.

Приложение запускается одним воркером намеренно: внутри процесса живёт фоновая
задача скачивания, а два параллельных воркера с одного адреса гарантированно
упрутся в лимит.
